# 인수인계 — 같은 방식으로 새 감시앱 만들기

> **다음 작업**: 야놀자에서 **화담숲** 예약 빈자리를 감시해 텔레그램으로 알리는 앱.
> 이 문서는 그 작업을 맡을 에이전트를 위한 것입니다. 웨딩홀 감시앱(`apps-script/Code.gs`, 1,164줄)을
> 만들면서 실제로 부딪혀 해결한 것들을 담았습니다. **같은 함정을 다시 밟지 마세요.**

---

## 0. 사용자에 대해 먼저 알아야 할 것

**비개발자입니다.** 용어를 모른다고 전제하고 안내하세요. 실제로 겪은 일:

- "편집기가 뭔데?" — Apps Script 편집기가 뭔지 몰랐습니다
- "6번을 어디 넣으라는거야" — "함수를 실행하라"와 "값을 넣으라"를 구분 못 했습니다
- 함수 선택 칸이 자동으로 안 바뀌어서 엉뚱한 함수를 실행했습니다

**그래서 이렇게 안내하세요.**

- 모든 단계에 **어디서 하는지**를 표시: 📱 텔레그램 / 💻 구글 편집기 / ⚙️ 프로젝트 설정
- "A-3", "B-2" 처럼 **번호를 붙여** 어디서 막혔는지 되물을 수 있게
- 한 번에 한 갈래만. 선택지를 늘어놓으면 멈춥니다
- 로그를 그대로 붙여넣게 하고, **어느 줄을 봐야 하는지** 짚어 주세요

## 1. 무엇을 그대로 가져갈 수 있나

`apps-script/Code.gs` 의 뼈대는 **대상 사이트와 무관**합니다. 사이트를 읽는 부분만 갈아 끼우면 됩니다.

| 그대로 쓰는 것 | 함수 |
|---|---|
| 알림 다채널 폴백 (텔레그램 → ntfy → 이메일) | `notify_`, `enabledChannels_` |
| 봇 둘로 나누기 (알림용 / 상태용) | `tgToken_`, `tgChat_`, `notifyStatus_` |
| 10분마다 갱신되는 고정 상태판 | `updateStatusMessage_`, `buildStatusText_` |
| 텔레그램에서 말 걸면 답하기 + 버튼 | `doPost`, `respondTo_`, `keyboard_` |
| 실패 감지·알림·복구 | `recordFailure_`, `recordPartial_`, `recordSuccess_` |
| 중복 알림 방지 상태 관리 | `readOpenSet_`, `forgetIfHallChanged_` |
| 설정·진단 | `showSettings`, `checkTelegramCommands`, `resetState` |
| 테스트 하네스 | `apps-script/test/run.js` (736줄, 90여 개 검사) |

**새로 만들어야 하는 것은 셋뿐입니다.**

1. `getCookie_` — 세션이 필요하면
2. `fetchOpenDays_` — 야놀자 응답에서 "빈자리 목록"을 뽑는 부분
3. 조회 단위 — 웨딩홀은 "달"이었습니다. 야놀자는 "날짜 범위" 또는 "객실"일 수 있습니다

## 2. 절대 다시 밟지 말아야 할 함정 6개

전부 실제로 당한 것들입니다.

### ① 텔레그램 웹훅 302 — 가장 오래 헤맸습니다

`doPost` 에서 `ContentService.createTextOutput()` 으로 답하면 구글이 **302 리디렉션**을 끼워 넣고,
텔레그램은 리디렉션을 따라가지 않아 `Wrong response from the webhook: 302 Found` 로 실패합니다.

```js
return HtmlService.createHtmlOutput('');   // ContentService 아님
```

진단할 때도 `followRedirects: false` 로 불러야 텔레그램이 보는 것과 같은 응답을 봅니다.
켜둔 채로 보면 리디렉션을 따라가 200 이 나와서 **정상인 줄 착각합니다.**

### ② 구글 무료 계정 트리거 실행 시간 = 하루 90분

넘기면 **구글이 트리거를 전부 꺼버립니다.** 그러면 실패 알림조차 안 와서 조용히 죽습니다.
`Utilities.sleep` 으로 기다리는 시간도 **그대로 실행 시간으로 잡힙니다.**

처음에 지터 0~90초 + 달 사이 1.2초로 잡았다가 **하루 180분**을 쓰고 있었습니다.
지금은 지터 0~10초, 간격 0.3초로 **1회 20초 / 하루 48분**입니다.

→ 새 앱에서도 **1회 실행 시간을 재서 상태판에 적으세요** (`dailyRuntimeText_` 참고).
   한도가 눈에 보여야 조용히 안 죽습니다.

### ③ ntfy.sh 무료는 IP 기준 하루 250통

Apps Script는 **구글 공용 IP**로 나가서 모르는 사람들과 할당량을 나눠 씁니다.
한 통도 안 보내고 `429 daily message quota reached` 를 맞습니다. 계정 토큰을 붙여도
무료 티어는 IP 기준이라 해결 안 됩니다 ([ntfy #1726](https://github.com/binwiederhier/ntfy/issues/1726)).

→ **ntfy 단독으로 쓰지 마세요.** 텔레그램을 1순위로, 이메일을 마지막 보루로 두세요.
   이메일은 `Session.getEffectiveUser().getEmail()` 로 설정 없이도 됩니다.

### ④ 조회 실패 시 상태를 덮어쓰면 중복 알림 폭탄

처음 코드는 일부 조회가 실패해도 그 결과로 상태를 덮어썼습니다. 그러면 실패한 부분의
항목들이 상태에서 사라지고, 다음 회차에 **전부 '새 빈자리'로 다시 알림**이 갑니다.

→ **이번에 확인하지 못한 것은 이전 상태를 이어받으세요.** 전부 실패하면 상태를 아예 건드리지 마세요.

### ⑤ 조용히 죽는 것이 가장 위험합니다

알림이 안 오는 상태에는 *빈자리가 없어서* 와 *확인 자체가 망가져서* 두 가지가 있습니다.
구분 못 하면 망가진 채로 몇 주가 갑니다.

→ 실패가 이어지면 **실패했다는 사실 자체를 알리세요.** 단, 일시적 흔들림과 진짜 고장은 나눠야 합니다.
   전체 실패 3회(30분) → 알림 / 일부 실패 12회(2시간) → 알림. 그리고 일시적 네트워크 오류
   (`Address unavailable`)는 2초 쉬고 한 번 재시도(`fetchWithRetry_`).

### ⑥ 텔레그램은 응답이 늦으면 같은 메시지를 다시 보냅니다

조회가 20초 넘게 걸리면 재전송이 걸리고, 그때마다 또 답해서 **같은 답장이 반복**됩니다.

→ `update_id` 를 봇별로 기억해 이미 처리한 것은 무시하세요 (`isNewUpdate_`).
   처리 **전에** 기록해야 도중에 실패해도 무한 루프가 안 됩니다.

## 3. 작업 순서 — 이 순서를 지키세요

### 0단계 · 사용자에게 먼저 물을 것

- **무엇을 감시하나요?** 화담숲의 *입장권*인지, *숙소*인지, *특정 날짜/객실*인지
- 야놀자 로그인이 필요한 예약인가요?
- 노리는 날짜 범위는?

화담숲은 곤지암 리조트와 엮인 상품이라 **야놀자에서 파는 게 정확히 무엇인지** 먼저 확정해야 합니다.
이걸 안 정하고 코드부터 쓰면 헛일이 됩니다.

### 1단계 · 3분 만에 판가름나는 것부터 (제일 중요)

**Apps Script(구글 미국 IP)에서 야놀자를 부를 수 있는가?**

이게 안 되면 나머지는 볼 필요도 없습니다. 웨딩홀 때는 운 좋게 열려 있었지만,
**야놀자는 상업 예약 플랫폼이라 봇 차단이 훨씬 강할 가능성이 큽니다.**

최소 코드로 먼저 찍어보게 하세요:

```js
function 접속테스트() {
  var res = UrlFetchApp.fetch('https://www.yanolja.com/...', { muteHttpExceptions: true });
  console.log(res.getResponseCode());
  console.log(res.getContentText().slice(0, 300));
}
```

| 결과 | 판단 |
|---|---|
| 200 + JSON/HTML 정상 | ✅ 진행 |
| 403 / 캡차 / 봇 차단 페이지 | ❌ Apps Script로는 불가 → 아래 **대안** |
| 로그인 페이지 | 로그인 자동화가 필요 — 난이도 급상승 |

**안 될 때의 대안**: 레포 루트의 Python 버전(`wedding_watch/`)처럼 Playwright로
실제 브라우저를 띄우는 방식. 단 **PC를 켜둬야** 합니다. 사용자는 그걸 싫어해서
Apps Script로 온 것이니, 안 되면 그 트레이드오프를 설명하고 선택하게 하세요.

### 2단계 · API 찾기

사용자에게 브라우저 개발자도구 캡처를 부탁하세요. **단계를 아주 구체적으로** 적어야 합니다.

1. 크롬에서 해당 예약 페이지 열기
2. **F12** → 위쪽 **Network** 탭
3. 날짜를 바꾸거나 조회 버튼 클릭
4. 새로 생긴 요청 중 JSON을 주는 것 클릭
5. **Request URL** 과 **Payload** 만 복사해서 전달

> ⚠️ **"Copy as cURL"은 쓰지 말라고 하세요.** 로그인 쿠키가 통째로 들어갑니다.
> URL과 Payload 두 개면 충분합니다.

### 3단계 · Code.gs 이식

`fetchOpenDays_` 만 야놀자 응답에 맞게 다시 쓰고, 나머지는 그대로 둡니다.
`HALLS` / `HALL_CODE` 같은 웨딩홀 전용 개념은 대상에 맞게 이름을 바꾸세요.

### 4단계 · 테스트

`apps-script/test/run.js` 가 Apps Script 런타임(`PropertiesService`, `UrlFetchApp`,
`MailApp`, `LockService`, `ScriptApp`, `HtmlService`)을 흉내 내서 `Code.gs` 를
`vm` 으로 그대로 돌립니다. **가짜 사이트만 야놀자 응답 모양으로 바꾸면** 나머지 검사는
거의 그대로 재사용됩니다.

```bash
node apps-script/test/run.js
```

상태 보존·채널 폴백·재전송 무시는 **깨져도 조용히 잘못 동작**하는 종류라,
테스트로 고정해 두는 값어치가 큽니다.

## 4. 하지 말아야 할 것

**자동 예약은 만들지 마세요.** 사용자가 코레일 건으로 물었을 때 정리한 기준입니다.

- 되돌리기 어려운 실제 결제·계약 행위입니다
- 로그인 정보를 스크립트에 저장해야 합니다
- 중간에 끊겨도 "성공"으로 보일 수 있는데, **잡힌 줄 알았는데 아닌 상태**가 최악입니다
- 대부분 이용약관 위반이고, 좌석·객실 선점은 **다른 사람이 못 잡게 막는** 행위라
  영향이 사용자 본인에게서 끝나지 않습니다

→ **알림까지만.** 대신 알림을 최대한 빠르고 눌러서 바로 갈 수 있게 만드세요.
